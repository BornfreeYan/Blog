## 引言
**从 Vibe Coding 到 Build Product**：
- Vibe Coding 是“用自然语言让 AI 帮你写程序”，降低“做出来”的门槛。
- 但不止是做出 Demo，而是走完完整产品闭环：**发现问题 → 验证需求 → 设计方案 → 构建产品 → 交付用户 → 说明价值 → 观察结果 → 持续迭代**。
  - AI 适合做小工具不断迭代，但不适合一键生成大型项目。大型项目仍需要人为拆流程、做架构、集成和测试。
  - Vibe Coding 时代的核心能力不再是记忆语法、手写代码、查文档，而是描述需求、code review、架构设计、问题排查，以及垂直领域知识、判断力等

### Claudecode
#### 安装
首先得有node.js 18+，然后：
```powershell
# 全局安装 Claude Code CLI
# 使用 -g 参数将命令安装到全局，这样在任何目录都能使用
npm install -g @anthropic-ai/claude-code

# 验证安装是否成功
# 如果显示版本号（如 0.1.25），说明安装成功
claude --version
```
或者可以直接安装 [CCSwitch](https://ccswitch.io/zh/)，然后点击里面的一键安装，里面可以一键安装很多 Agent，并帮你配置好你的 Coding Plan，方便接入 Claude Code。
#### 核心技巧

| 技巧、命令 | 怎么用 | 关键点 |
| --- | --- | --- |
| **双击 Esc 回退对话** | 按一次清输入，按两次回退上一轮，按三次清空历史 | ⚠️ 只回退**对话**，不撤销已改的文件；改文件前先 `git commit` 或 `git stash` |
| **@ 引用文件** | `@src/utils.ts 解释这个文件` | 比模糊描述更准，也省 Token；支持目录、多文件、`@file.ts:45-60` 行范围；输入 `@` 后按 Tab 补全 |
| **! 执行命令** | `!npm test`、`!git status` | 不用切终端；敏感命令（`rm -rf`、`sudo`）会先询问 |
| **/plan 先规划后编码** | `/plan` 后描述任务 | 复杂任务先出分阶段计划，再逐段执行；超过 30 分钟的任务建议先用 |
| **/init 生成 CLAUDE.md** | `/init` | 自动扫描项目、技术栈、命令、规范，生成“项目记忆”；新项目初始化后立即跑。你也可以自行建立CLAUDE.md或者AGENTS.md，内含技术栈、代码规范、常用命令和skill等 |
| **/compact 压缩上下文** | `/compact` | 长对话 5～6 轮后用，提取关键信息生成摘要，省 Token；想清除所有context用/clear |
| **Git 提交工作流** | `/diff` → 让 Claude 生成 commit message → `!git add -A` → `!git commit -m "..."` | 先看 diff 再提交 |
| **Ctrl+C 取消操作** | 按一次取消当前操作，按两次退出 | 和双击 Esc 不同：Ctrl+C 停**正在执行的操作**，Esc 回退**对话状态** |
| **/context 查看上下文** | `/context` | 看 Token 使用率、大文件、对话轮数；超过 70% 考虑 `/compact` |
| **/resume 恢复会话** | `/resume` | 多任务之间切换，保留各自上下文；和 `claude -c`、`claude -r` 区分 |
| **/help显示所有命令** | `/help` | 忘了命令时看一下 |
| **/model切换模型** | `/model` |  |
| rules文件 | 在项目级或者用户级的.claude文件夹内新建rules文件夹，里面存放一些markdown文件 | 把一些规则从CLAUDE.md中抽取出来放在rules里面（模块化管理），防止CLAUDE.md过于臃肿 |
#### MCP
**MCP 让 Claude Code 从“只能读写本地文件”变成“能连 GitHub、数据库、API、浏览器”的超级助手。**

MCP配置文件的位置：
| 级别 | 路径 | 作用范围 |
|---|---|---|
| 用户级 | `~/.claude.json` | 所有项目 |
| 项目级（推荐） | `.claude/mcp.json` | 当前项目。项目级的好处：可提交 Git、团队共享、不同项目用不同 MCP、不污染全局。 |

想添加MCP可以直接说人话
```text
帮我添加 GitHub MCP 服务器，我的 token 是 ghp_xxx
```

在新的对话中就可以输入/mcp，查看已安装的mcp，也可以说“把当前修改推送到 GitHub，创建 PR，标题是‘添加新功能’”。

不过项目级的配置可能被提交，那么需要保护好自己的token:
```json
{
  "mcpServers": {
    "github": {
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-github"],
      "env": {
        "GITHUB_PERSONAL_ACCESS_TOKEN": "${GITHUB_TOKEN}"
      }
    }
  }
}
```
GITHUB_TOKEN会从本机或本项目的环境变量获取，而不会上传云端。
#### Skills
**Skills 是把“怎么做”打包成可复用技能包，让 Claude Code 从“通用助手”变成“懂你项目和流程的团队成员”。** 本质上就是一个 Skill.md 文件，加上一堆脚本等附属文件。解决四个问题：重复指令复用、知识无法沉淀、标准不统一、效率低。

skill的位置：
| 类型 | 位置 | 作用范围 | 适用 |
|---|---|---|---|
| 全局 Skills | `~/.claude/skills/` | 所有项目 | 个人通用技能 |
| 项目 Skills | `项目/.claude/skills/` | 当前项目 | 团队共享、项目规范 |

skill结构一般是：
```markdown
---
name: skill-name          # 必填，小写字母、数字、连字符
description: 简短描述      # 必填，越具体越容易被自动匹配
category: development     # 可选
tags: [code, automation]  # 可选
allowed-tools: "Bash(pdftotext:*)"  # 可选，临时授予工具权限
---
```

skill的一些内部机制：

- **三层渐进加载**：启动只加载 name + description（约 30～50 tokens/个）；触发时才加载完整 SKILL.md（约 5,000 tokens）；脚本和参考文档按需读，不占上下文。
- **纯 LLM 推理路由**：没有硬编码关键词匹配，靠 Claude 自己理解用户意图去匹配 description。
- **双上下文注入**：触发时给用户看“skill is loading”，同时把完整指令作为隐藏消息注入 AI；还能临时改工具权限、切模型、隔离上下文。
- **用完即弃**：任务完成后完整指令从上下文移除，只保留对话历史。

## 网络相关
URL、http、端口、本地服务
- URL（网址）：就是浏览器地址栏那一串东西，比如：https://www.trae.cn/ http://localhost:3000/
- HTTP / HTTPS：在 URL 开头看到的 http:// 或 https://：
  - HTTP：普通传输方式；
  - HTTPS：多了一层加密，更安全。
- 端口（Port）：可以把一台电脑想象成一栋大楼，端口就是每个房间的门牌号：`:3000` 表示 3000 号房间；同一台电脑上，可以同时开多个服务，各占一个端口。http://localhost:3000 就是“访问我自己电脑上 3000 号房间里跑着的那个服务”。
- 本地（Local / localhost）:指的就是你自己的电脑。localhost 可以理解为“这台机器自己”。当你访问 http://localhost:3000 ，其实是在跟自己电脑上运行的程序打交道，而不是上网访问别人家的服务器。

### UI设计
**面对一个设计精美的网页/APP，如何分析它、借助 AI 设计工具临摹到“以假乱真”，并最终沉淀出自己的设计系统。**

整体路径可以概括为：**学会看设计 → 掌握拆解方法 → 认识两类 AI 设计工具 → 实战临摹 → 设计转代码 → 沉淀设计系统 → 守住版权边界。**

- **前端设计入门，从“抄”开始**
   - 入门最快的方式是临摹，而不是凭空创造。临摹会强迫你还原过程：测量间距、查色值、比较层级。
   - 设计的“好看”可以被量化：色值、字号、间距、圆角、阴影都是数字。
   - 参考网站清单：[Awwwards](https://www.awwwards.com) 、[Recent（原 Godly）](https://godly.website) 、 [Landbook](https://land-book.com) 、[Lapa Ninja](https://www.lapa.ninja) 、[Mobbin](https://mobbin.com) 、[Dribbble](https://dribbble.com) 、[Behance](https://www.behance.net)

- **会看才会设计——拆解一个页面**
   - **看结构**：现代网页通常拆为导航栏、首屏 Hero、内容区 Sections、页脚 Footer 四大块。
   - **看视觉**：4 个可量化要素——色彩、字体、间距、圆角与阴影。当然也可以直接截图丢给大模型。
     - 色彩：主色、背景色、文字色，用取色器取Hex值
     - 字体：标题/正文用什么字体、几号、多粗，浏览器 DevTools 里看 font-family/size/weight
     - 间距：区块之间、卡片内部的留白，记下常用的 8 / 16 / 24 / 48 px 节奏
     - 圆角与阴影：卡片、按钮的圆角半径与阴影强度，DevTools 里看 border-radius / box-shadow
   - **看组件**：把按钮、卡片等拆成可复用零件，记录样式参数，逐步形成自己的组件样式库。
   - **翻译给 AI**：把看到的设计写成结构化描述（结构、配色、字体、间距、圆角、阴影），看得越细，AI 抄得越准。

- **AI 时代的前端设计工具全景**
   - **路线一：Figma**——专业设计稿工具，适合可编辑、可协作、像素级可控的严谨交付，在画布里搭布局、调组件、做交互原型
   - **路线二：Claude Design / Open Design**——对话式 AI 设计画布：
     - [Open Design](https://open-design.ai/zh/) 是 Claude Design 开源平替，本地优先、BYOK、不绑定 Agent；核心概念是 Skills、Templates、Design Systems（151 套可移植设计系统）。它会检测本地的 Agent，比如说 Claude Code 作为设计引擎。
     - UI design Skill（如 frontend-design）可把设计规范打包成 AI 可执行指令。
   - 两条路线可组合：快速出原型 → 导入 Figma 精修 → 交给 Claude Code 写代码。

- **实战一——把别人的网页临摹到像**
   - 五步法：选定目标 → 用第 2 章框架拆解 → 喂给 AI 设计工具生成第一版 → 逐区块对照迭代 → 像素级对比验收。
   - 验收标准：原网页与临摹版并排放大，色值、字号、间距、圆角肉眼看不出差异；缩到 50% 仍分不清。
   - “像”不是目的，而是手段；临摹 2-3 个不同风格网站后会积累设计手感。

- **实战二——从设计到代码**
   - 路径 A：AI 设计工具 → 前端代码（Claude Design 的 `/design-sync`、Open Design 导出 HTML、Figma/MasterGo 插件或 MCP 导出 React/Vue）。
   - 路径 B：截图 → 多模态大模型还原成 React 组件。

- **把大厂的设计系统变成自己的**
   - 设计系统本质是：颜色 Token + 字体规范 + 间距节奏 + 组件样式 + 使用约定，可写成 `DESIGN.md`。
   - 三步建立自己的设计系统：选基底（套用大厂规范）→ 改参数（品牌色、圆角、间距）→ 沉淀成文件或 Skill。

- **版权与伦理**
   - **抄规则不抄结果**；商用项目确认素材、字体授权与参考网站条款；关注 AI 生成内容归属；敏感场景人工审核。
   - 学习与原型阶段可放开临摹，商业交付时把“参考”变成“自己设计系统的再创作”，并保留生成记录。

### 从设计到代码
**如何把 Figma 等设计工具里的原型，转化成真正能在浏览器中运行的前端代码。** 
#### 从原型到代码的三种路径
| 路径 | 方法 | 特点 | 适用场景 |
|------|------|------|----------|
| 路径一 | 多模态大模型看截图直接还原代码 | 灵活、无需特定工具 | 快速原型验证、简单页面 |
| 路径二 | 平台自身能力或插件导出代码 | 还原度高、可编辑性强 | Figma 用户 |
| 路径三 | 平台结合 MCP 能力导出代码 | 自动化程度高、可定制 | 需要深度集成的工作流 |
#### 多模态 AI 直接还原代码
**操作流程：**

1. 在 Figma 中把页面导出为 PNG 或 JPG 截图，确保包含完整布局。
2. 选择支持图像输入的模型。
3. 编写提示词，例如要求使用 Flexbox/Grid、响应式设计、包含所有可见 UI 元素、尽量还原颜色与字号。
4. 让模型返回完整 HTML 代码，保存为单个 `.html` 文件本地测试，后续再转成 React 等框架。
#### 平台自身能力或插件导出代码
**Figma Make：**
- Figma 官方 AI 设计工具，可根据提示词或参考图高精度还原网页原型 UI。
- 特点：高精度还原、生成结果可转回可编辑的 Figma Design 文件、支持 GitHub 集成。
- 完整功能需要 Pro 权限，学生可通过教育认证免费获得。
- 操作步骤：进入 Figma Make → 上传参考图 + 提示词 → 查看渲染结果 → 点击右上角编辑器图标回到 Figma Editor 调整 → 导出代码或连接 GitHub 保存。
#### 平台结合 MCP 能力导出代码
**AI 模型 ←→ MCP 服务器 ←→ 设计工具（Figma/MasterGo）**

1. AI 模型通过 MCP 向设计工具发送请求；
2. 设计工具返回结构化设计数据（图层、样式、组件等）；
3. AI 理解设计结构并生成代码；
4. 代码可直接导出或同步到开发环境。

例如Figma MCP:
- 安装 MCP 服务器：`npx figma-mcp-server`
- 在 Claudecode 等工具中配置 `mcpServers`，填入 Figma Access Token（Figma → Settings → Personal Access Tokens 生成）。
- 在 AI 工具中启用 MCP 连接，提供设计文件链接，AI 自动读取图层树、理解组件结构并生成 React/Vue 组件；还可继续对话迭代，例如“把按钮提取为独立可复用组件”。

## 后端
>用户看不见在服务器上跑的那部分，存数据、读数据、执行业务规则
>前后端的交互相关名词：
>1. 接口：约定一个地址、某一个格式来交互
>2. 请求（Request）：前端给后端的一次提问，需要有 URL（请求去哪儿）、用了什么方式（比如 GET、POST）、带了什么参数
>3. 响应：后端给前端的回复，比如说状态码以及实际数据，实际数据大概率是 JSON

## 数据库
### 什么是数据库
**数据库解决什么：** 持久化存储、快速查询、高并发、数据一致性、安全性。

**两类数据库：**
| 类型 | 像什么 | 优点 | 缺点 | 适合 |
|---|---|---|---|---|
| **关系型（SQL）** | 严谨的 Excel 表格，表之间用外键关联 | 数据精确、一致性强、复杂查询方便 | 改结构麻烦、海量数据性能受限 | 金融、库存、订单、账务 |
| **非关系型（NoSQL）** | 灵活文件夹，一个文档装完整业务信息 | 结构灵活、读取快、易扩展 | 有冗余、关联查询弱 | 社交内容、日志、物联网、推荐系统 |

**SQL 示例：** 用户、文章、评论、标签拆成 5 张表，查询时用 JOIN 拼起来。
**NoSQL 示例：** 一篇文章连同作者、评论、标签全塞进一个 JSON 文档，一次读取就拿到全部。

### 筛选值得做的方向
>    详见：[筛选方法](https://datawhalechina.github.io/easy-vibe/zh-cn/stage-1/finding-great-idea/#%E9%99%84%E5%BD%95-sop-%E6%96%B9%E6%B3%95%E8%AE%BA)
#### 找需求
首先要明确需求，先确认有人愿意为这个痛点买单，比如傻乎乎地做 to-do list 有啥用呢？
**需求三层：痛点、爽点、痒点**
| 类型 | 本质 | 例子 | 付费意愿 |
|---|---|---|---|
| **痛点** | 恐惧驱动，不解决会很难受 | 糖尿病患者不知道吃多少碳水会血糖飙升 | 强，是“止痛药” |
| **爽点** | 即时满足，产生愉悦感 | 外卖 30 分钟送达、一键生成 PPT | 中等，单独付费点较弱 |
| **痒点** | 虚拟自我，想要更好但不是必须 | 记录每天喝多少水、AI 艺术滤镜 | 弱，是“维生素” |

- 优先级建议：**痛点 > 爽点 > 痒点**。
- 常见错误：**用痛点的方式推销痒点产品**，比如“记录喝水能让你更健康”，用户不会买账。

**验证真需求的 5 步法：**

1. 找 10 个目标用户聊天，问“你现在怎么解决这个问题”。
2. 分析现有替代方案，找出你的优势。
3. 测试付费意愿：做预售或收定金。
   - 超过 10% 愿意付定金：需求真实，值得投入。
   - 5%～10%：需求存在，但需要打磨。
   - 低于 5%：需求可能不成立。
4. 估算市场规模：目标用户数 × 付费意愿 × 客单价。
5. 思考护城河：技术难度、网络效应、品牌、成本优势。

#### 深挖方向和解决方案
- 首先是从自己出发，你天然理解这个群体，或者从属于这个群体。比如说是刚生完孩子的宝妈，需要减肥健身，但是大多健身软件不考虑产后女生的实际情况
- 所以就需要横向切分人群，想健身的人可以分为增肌人群、减肥人群、学生等等，不切分的话，难赢大平台，细分人群需求反而更痛
- 接下来就是纵向深挖场景，针对这一群体、这一需求优化功能，不断探索迭代，完成价值构建

#### AI 对话打磨

1. 抛出原始想法，告诉 AI 你的担忧。
2. 让 AI 帮规划 MVP：分几个阶段、每阶段目标、技术难度。
3. 提出你的担忧：技术、内容、推广、获客。
4. 让 AI 提供解决方案，多方案对比、成本估算。
5. 最终确认计划，设定验证指标。

### 看懂真实需求（Job to be done）
**用户不是买功能，而是在具体场景里“雇用”产品完成一个进展。**

**要点：**

1. **从功能转向任务**  
   不问“要什么功能”，问“他为什么此刻要用”。竞品不只是同类 App，也包括 Excel、手工、找同事、拖着不做。

2. **JTBD 五要素**  
   场景、触发、想完成的进展、当前替代方案、成功标准。没有场景的需求通常不真实。

3. **万能句式**  
   > 当……的时候，我想要……，以便于……。  
   > 现在我只能通过……来勉强完成这件事。

4. **三层 job**  
   功能层、情绪层、社会层。只做功能层容易被替代；付费意愿常来自情绪层和社会层。

5. **筛点子 5 问**  
   场景够具体吗？用户已有笨办法吗？痛感够强或够高频吗？做好后状态会明显变好吗？第一版能只做关键一步吗？

6. **访谈别问“你想要什么功能”**  
   问最近一次真实经历：当时卡在哪、怎么解决、最烦最慢最不放心的是什么、什么结果算真的有用。

7. **AI 的用法**  
   把用户原话整理成 JTBD 假设；把模糊点子拆成几个场景；让 AI 当反方挑刺。原则是：**AI 帮你整理，不替你臆测用户。**

8. **四个误区**  
   把 job 写成功能名；人群写得太宽；只听用户说、不看用户做；一上来就想做完整平台。

### 用访谈验证需求（The Mom Test）
**别问“你会不会用”，要问“你上次怎么处理的”。**

问“你觉得这个想法怎么样”“有产品你会用吗”，得到的往往是“挺好的”“应该有用”。这不代表需求存在，只代表你问了一个很容易得到好听答案的问题。妈妈、朋友、同事都会礼貌性鼓励你。

**三个原则：**

1. **少谈你的点子，多谈用户过去的经历。**
2. **少问抽象意见，多问具体事实。** “我上周为这事折腾了 2 小时”比“听起来不错”有用。听到抱怨才是最好的
3. **少问用户想要什么方案，多看他现在怎么解决。**

**访谈顺序：**

1. 开场说明“我是来学习的，不是推销”。
2. 从最近一次真实经历问起。
3. 追问行为、成本、替代方案。
4. 最后再判断痛感和优先级。

**和 JTBD 怎么配合：**

- JTBD 帮你提出需求假设。
- The Mom Test 帮你访谈验证假设。
- 先 JTBD 写一句假设，再用“最近一次”“当时怎么处理”“哪步最卡”去问。

**AI 能帮什么：**

- 把你的问题从“问意见”改写成“问过去行为”。
- 针对不同访谈对象生成提纲。
- 整理访谈记录，区分“事实”和“意见”。
- 复盘你的访谈，指出哪些问题像在找认可。

**五个新手误区：**

1. 把访谈做成产品介绍会。
2. 只找熟人聊。
3. 问题没搞清就追功能细节。
4. 把“我会用”当成验证结果。
5. 访谈完不整理。
### 收敛方案（双钻模型）
**先把问题搞清楚，再想解决方案；两次“先发散、再收敛”。**

**双钻四步：**

| 阶段 | 做什么 | 产出 |
|---|---|---|
| **Discover 发现** | 广泛看用户、场景、现有做法、替代方案 | 一堆真实材料 |
| **Define 定义** | 从材料里收出“这次先解决哪一个问题” | 一句清晰的问题定义 |
| **Develop 发展** | 围绕这个问题，想多种方案 | 几个候选方案 |
| **Deliver 交付** | 选一个做最小原型，拿去测试 | 可验证、可迭代的东西 |

**为什么要把问题和方案分开？**

常见错误流程：想到点子 → 觉得酷 → 马上画原型 → 功能越来越多 → 最后**不知道自己在解决什么问题**。

双钻就是防止你：
- 选错问题
- 误解用户
- 过早锁定方案
- 细节打磨很久，方向却没验证

**一句话区别：**

- **Discover 发散**：别太早以为自己知道答案。
- **Define 收敛**：从“问题很多”收到“这次先解决哪一个”。
- **Develop 发散**：围绕同一个问题，多想几种做法。
- **Deliver 收敛**：选一个最小版本，放进真实环境验证。

**好问题定义长什么样？**

不要写：“我想做一个提高开会效率的 AI 工具。”
要写：“项目型团队在 30～60 分钟协作会议结束后，无法在 10 分钟内输出带待办、责任人和截止时间的纪要。”

也就是：**用户是谁、场景是什么、卡点是什么、成功标准是什么。**

**四个常见误区：**

1. 还没 Discover，就直接 Deliver——刚有想法就画原型、写代码。
2. Discover 太久，始终不 Define——一直调研，不敢收敛。
3. Define 之后又偷偷改问题——因为某个方案好做，就反过来改问题。
4. 把 Deliver 误解成“大而全上线”——其实一个可测试的原型、一轮真实试用，也算 Deliver。

**AI 产品特别容易掉的坑：**

能力先行：一上来就想接多模态、做 Agent、加工作流。
双钻会逼你先问：用户到底卡在哪？这个卡点非 AI 不可吗？不用 AI 现有办法差在哪？

**可以直接套用的模板：**

- **Discover**：用户是谁？最近一次遇到问题是什么时候？现在怎么解决？最烦最慢最不放心的是哪一步？
- **Define**：最值得先解决哪一个？哪个场景最高频或最关键？第一版只服务谁、只解决什么？成功后用户状态会变成什么样？
- **Develop**：有哪些可能方案？哪个最轻、最快、最容易验证？哪些必须做，哪些以后再说？
- **Deliver**：最小能交付什么来验证？流程图、原型还是 MVP？找谁测？测完怎么判断继续、修改还是放弃？

### 做出可交互原型
**写代码前，先搞清“谁、在什么场景、要解决什么”，然后先做单页跑通核心流程，再扩成多页面。**

**整体四步：**

1. **需求分析**：从模糊业务目标收到一页需求说明。需要理解使用者（用户故事和具体场景）、定义结果功能需求、控制功能的范围
2. **单页验证**：先做一个页面，跑通核心流程。
3. **多页扩展**：补导航、列表、设置等页面。
4. **美化完善**：走完整流程，补加载、反馈和边界情况。

### 打磨和交付
**别再加新功能，把现有产品完整用一遍，请别人试，把卡住的点补好，再发出去。**
- 先像用户一样走完整流程，不看代码，只看页面，从头到尾用一遍
- 补四个最容易卡住的地方

| 时刻 | 要补什么 |
|---|---|
| **刚打开** | 一句用途说明、一组示例内容、标明支持的图片格式和大小；字段太多就收，必填只留生成真正需要的 |
| **点了按钮** | 显示“生成中”，暂时禁用按钮防重复提交；已填内容不要消失，页面不要跳空白 |
| **结果出来** | 提供编辑、复制、下载、重新生成；模型不确定的信息标出来让用户补或删 |
| **请求失败** | 说明这次没完成，给重试或返回修改入口；格式不支持就说明支持哪些；必填缺失就在字段旁提示；失败后保留已填内容 |

- 请别人来试，告诉他目标，然后观察他的停顿、重复点击需要你解释的地方，采访他使用感受
- 按优先级优化：无法完成任务>操作容易误解>操作成本过高/步骤重复>样式和新增功能
- 整理好再分享：准备好可运行的应用、30到60秒演示视频、README项目说明(介绍目标用户、核心问题、主要流程、用户反馈)
